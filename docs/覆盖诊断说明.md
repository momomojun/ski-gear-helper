# 数据覆盖诊断（第一阶段）

在项目根目录运行：

```powershell
.venv/Scripts/python.exe scripts/diagnose_coverage.py
```

默认生成三份本地文件，不联网，不修改抓取代码、数据库或正在运行的任务：

- `data/diagnostics/coverage-report.md`：概览、统计口径、分级修复清单和按站核查队列。
- `data/diagnostics/coverage-details.md`：每个网站 × 分类的基线、当前状态、最后记录成功时间、库存年龄、覆盖风险和日志证据。
- `data/diagnostics/coverage.json`：以上结构化数据，包括配置入口、预算和分类状态原始消息。

`data/` 被 Git 忽略，报告不自动上传。重复执行会更新这三份文件；要保留一次验收快照，使用 `--out data/diagnostics/stage1-baseline`。可用 `--db`、`--log` 指定输入。

## 如何阅读

固定基线选择最后一轮已完成、未指定商家且覆盖全部滑雪分类的任务。后台更新仍在进行时，不用它替代已完成基线。当前库存与分类状态通过同一 SQLite 只读事务取得；日志单独读取，不保证与数据库原子同步。

当前启用分类用于概览统计；已停用或历史残留分类仍列在明细中。因此它与不限制启用配置的数据库商品总数不同。户外专属分类保留在明细及 JSON，滑雪统计包括两专区共享分类。

状态与证据须分开看：

- `ok + 0` 只表示零结果待核查，不能证明真实空目录，也不能证明解析失败。
- `ok + 有产出` 不证明全量覆盖或价格准确。第二阶段已修复通用适配器吞异常和不完整状态传递；旧记录仍可能受旧逻辑影响，须在重启后抓取验证。
- 明确 `partial` 才统计为部分覆盖；代码中的页数/详情上限另列为风险，不能断言某次实际触顶。
- 基线任务中的分类 `n` 包含改判到其他分类的产出；当前分类状态的 `n` 不包含，不能直接计算增长率。
- 最后成功时间仅指历史任务摘要或当前分类状态记载的 `ok + 有产出`，不等于独立核验通过。未知保持未知。
- 活跃记录不代表仍有货；7 天未见只是诊断指标，以数据库最新商品时间为参照。数据库时间戳无时区，保留原值。
- 站级历史日志带行号及时间，不自动归因到当前所有分类。网页 404 等证据尚未联网复核。
- `running` 可能是中断后残留状态，不能据此推断进程正在运行。
- 新版 `empty` 表示零结果待核查，不作为成功，不据此下架旧商品。

## 后续修复顺序

先修复状态传递和部分抓取的数据保留，再修原价证据与报价时效，然后逐站核对入口、平台、分页和详情覆盖。第一阶段只诊断，不执行这些修复。

诊断工具的针对性验证：

```powershell
.venv/Scripts/python.exe -m pytest tests/test_coverage_diagnosis.py -q
```
